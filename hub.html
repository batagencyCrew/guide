Required for every automation

Every site automation must integrate with the Bambou Automation Hub v2, in addition to the Bambou AI API. Your site automation is not finished until it is connected and verified in the HUB.

In v2, each site has one script on one VPS supervised by bambou-agent (agent2/). Your script imports the bambouhub SDK (Python or Node.js) and talks to the agent over a local Unix socket (HUB_AGENT_SOCKET). The agent owns the HUB token, syncs config files, buffers offline telemetry, reports host metrics, and uploads backups; the HUB does not implement your site's automation, AI generation, or captcha solving.

your script + bambouhub SDK ── unix socket ── bambou-agent ══ WSS/HTTPS ══ https://bamboubot.duckdns.org
Public dashboard / HUB origin: https://bamboubot.duckdns.org
Agent transport: wss://bamboubot.duckdns.org/ws/site + https://bamboubot.duckdns.org/api/agent/v2/*

Set HUB_URL=https://bamboubot.duckdns.org in the agent config — origin only, never localhost in production. The script itself never holds HUB_AGENT_TOKEN.

Setup and starter downloads

  1. Ask BIPRO/Bambou to create or assign your site in the dashboard (Overview → Add site) and provide its one-time site agent token (hst_...). Keep it only in the agent's private root-owned config file.
  2. Download the v2 documentation + starter package. It contains the v2 docs, bambou-agent (agent2/), Python and Node.js bambouhub SDKs (sdk/), runnable Python and Node.js starters (templates/v2/), and the systemd unit (deploy/bambou-agent@.service).
  3. Install bambou-agent (Python 3.10+) into /opt/bambou-agent with a venv from agent2/requirements.txt, and copy your chosen starter (templates/v2/python or templates/v2/node) plus the matching SDK into /opt/scripts/<site>/. See Connecting a script to the hub for exact commands.
  4. Replace every TODO block in the starter (settings reload, prices, open_session, do_task, close_session, custom commands, optional balances) — or add the bambouhub SDK directly to an existing script.
  5. Create /etc/bambou-agent/<site>.conf (owner root, mode 0600) as shown below, install bambou-agent@.service, and enable systemctl enable --now bambou-agent@<site>.
  6. In the dashboard, configure secrets/presets/proxies in the site's Configuration, Files, and Proxies tabs, set a backup destination, press Start, and run the verification checks below before handoff.
HUB_URL=https://bamboubot.duckdns.org
HUB_AGENT_TOKEN=hst_replace_with_your_site_agent_token
HUB_SCRIPT_DIR=/opt/scripts/mysite
HUB_SCRIPT_COMMAND=/opt/scripts/mysite/.venv/bin/python main.py
HUB_FILES=config.json,.env,proxies.txt
HUB_STATE_DIR=/var/lib/bambou-agent-mysite

These are example paths and a placeholder token, not credentials. Note that proxies.txt, proxies.json, and .bambou-config.schema.json in HUB_SCRIPT_DIR are also auto-discovered unless --no-auto-files is set. Run one bambou-agent per site token.

What you must wire up

  • Workers & health: wrap each parallel unit (thread, asyncio task, process, or browser) with with hub.worker(name) as w: (Python) or hub.worker(name) (Node.js). Update w.running(), w.idle("reason"), w.error("reason"), and w.task_done() / w.taskDone().
  • Logs: call hub.install_logging() (Python) or hub.captureConsole() (Node.js) and use w.log.* so every level and traceback reaches the HUB, attributed to the active worker.
  • Metrics, costs & balances: report real counters/gauges/timings (hub.count, hub.gauge, hub.timing), record spend via hub.set_price + hub.add_cost / with hub.cost(...) wherever money is spent, and optionally report provider balances via hub.balance(..., low=...).
  • Proxy health: report proxy results with hub.proxy(label, state, url=proxy_url) using states ok | slow | blocked | auth | timeout. Proxy credentials are never sent; only the proxy key hash is emitted.
  • Config files, dynamic schema & proxies: read settings from config.json, .env, and proxies.txt, reload on @hub.on_config_change / hub.onConfigChange, and optionally call hub.declare_config_schema(...) (or ship .bambou-config.schema.json) for typed forms and live BambouBotAI preset pickers.
  • Lifecycle controls, commands & issues: honour hub.stopping, hub.wait_if_paused(), and hub.desired_workers; register custom dashboard/bot actions with @hub.on_command / hub.onCommand; raise human-actionable problems with hub.issue(...) (forwarded to Discord/Telegram via BambouBot).
  • Backups: keep HUB_SCRIPT_DIR clean and omit --no-backup so bambou-agent packs the script directory (excluding .git, node_modules, __pycache__, .venv, venv, and state dir) and streams it to the HUB for cloud transfer via rclone.

Read Connecting a script to the hub, Script starters (hub v2), and Architecture for full usage and examples.

Agent v2 & SDK reference

Scripts use the bambouhub SDK over the local Unix socket (HUB_AGENT_SOCKET) and do not call HUB HTTP endpoints directly. bambou-agent communicates with https://bamboubot.duckdns.org using Authorization: Bearer <site-agent-token>:

Method / pathPurpose
GET /ws/siteWebSocket for instant command push, file-change notifications, and batch telemetry.
GET /api/agent/v2/whoamiVerify site token, resolve site metadata, and read desired_state.
POST /api/agent/v2/batchSend presence, workers, host metrics, logs, metrics, costs, balances, proxy observations, issues, and command acks.
GET /api/agent/v2/commandsHTTP polling fallback for pending lifecycle and custom commands.
POST /api/agent/v2/commands/{id}/ackAcknowledge command execution status (running, completed, failed).
GET /api/agent/v2/filesFetch managed config files and revisions from the HUB.
POST /api/agent/v2/files/ack · /files/pushAcknowledge applied HUB edits or push hand-edited local file changes.
GET /api/agent/v2/backups/configFetch scheduled backup settings and excludes.
POST /api/agent/v2/backups/uploadStream packed .tar.gz codebase archive to the HUB for rclone transfer.

Note: legacy v1 routes under /api/agent/* remain available only as a compatibility layer for unmigrated scripts; all new scripts must use v2 (bambou-agent + bambouhub SDK).

Public connectivity check (no credentials):

curl --fail https://bamboubot.duckdns.org/api/health
# Expected: {"status":"ok"}

Verify before handoff

  • bambou-agent@<site> runs as a systemd service, starts on boot, and reconnects automatically after network drops or HUB restarts (with offline disk spooling intact).
  • Dashboard shows the site online with real worker statuses, task counts, host CPU/RAM/disk, and live per-worker logs.
  • Start, Stop, Restart, Pause / Resume, Set workers, and any custom commands execute cleanly and report completion.
  • Managed files (config.json, .env, proxies.txt) sync both ways; dashboard edits reach disk within seconds, trigger on_config_change, and secret fields stay masked without secrets:reveal.
  • Real metrics, costs, and proxy health observations appear in the dashboard (and optional balances / hub.issue alerts route to Discord/Telegram if configured).
  • An on-demand backup succeeds from the agent through the HUB to the assigned cloud destination.

Credentials, retries, and limits

Keep HUB_AGENT_TOKEN (hst_...) only in /etc/bambou-agent/<site>.conf (mode 0600). Never commit tokens or expose HUB_AGENT_TOKEN to the automation script environment; the agent connects to the HUB and exposes only a local Unix socket to the script.

Secrets in .env / JSON (and fields marked secret: true in config_schema) plus proxy passwords are masked as ******** in the dashboard unless the viewer holds secrets:reveal and explicitly reveals them (which is recorded in audit_log). Log ingestion preserves tracebacks for internal troubleshooting and gates log reads by sites:view and site_scope.

bambou-agent spools batches to HUB_STATE_DIR when the HUB is unreachable and deduplicates command deliveries. Keep secrets out of source code and treat whole-codebase backup archives as sensitive since HUB_SCRIPT_DIR may contain .env; cloud storage credentials belong only on the HUB.
